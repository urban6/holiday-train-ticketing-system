# 실험 1 — 요청 1,000건은 대기자 1,000명인가?

이번 단계의 목표는 요청 수와 실제 저장된 대기자 수의 차이를 설명하고 검증하는 것이다.
2026-09-22에 로컬 Redis 8.6.2에서 실행했다. 원본은
[redis-benchmark-members-result.json](redis-benchmark-members-result.json)에 보관했다.

## 실험 조건과 실행

- 애플리케이션의 `server/src/main/resources/redis/enqueue.lua`를 그대로 실행한다.
- 각 경우 요청 1,000건, 동시 연결 10개, 파이프라인 1개다.
- 임시 Unix 소켓으로 독립 Redis를 띄운다. 기존 Redis에는 접속하지 않는다.
- 승격·회수·이탈은 없고, 키 만료 전에 결과를 읽는다.
- 경우마다 빈 키에서 시작하고, 마지막에 임시 Redis를 종료한다.

프로젝트 루트에서 실행한다. Python 3와 PATH에 등록된 `redis-server`, `redis-cli`,
`redis-benchmark`가 필요하다.

```bash
python3 k6/check-benchmark-members.py
```

자신의 결과를 원본 실측과 별도로 저장하려면 다음처럼 실행한다.

```bash
python3 k6/check-benchmark-members.py --output /tmp/benchmark-members.json
```

스크립트는 시퀀스가 1,000인지, waiting과 poll의 개수 및 멤버가 일치하는지,
난수 치환 여부를 검사한다. 조건이 어긋나면 오류로 종료한다.

## 실측 결과

| 조건 | 요청 수 | GET seq | ZCARD waiting | ZCARD poll | 기존 대기 멤버 갱신 횟수 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `-r` 없음 | 1,000 | 1,000 | 1 | 1 | 999 |
| `-r 1000` | 1,000 | 1,000 | 608 | 608 | 392 |
| `-r 1000000` | 1,000 | 1,000 | 999 | 999 | 1 |

난수 결과는 다시 실행하면 달라질 수 있다. 608명이나 999명 자체를 정답으로 검사하지 않는다.
이번 실험은 데이터 개수 검증이다. 워밍업 없는 짧은 로컬 실험이므로 원본 출력의 req/s를
기존 AWS 성능이나 Redis 처리 한계와 비교하지 않는다.

## 왜 이런 결과가 나왔는가?

### 1. `-r`이 없으면 멤버가 변하지 않는다

기존 벤치마크는 `m:__rand_int__`를 넘기지만 난수 치환 옵션이 없다.
따라서 매번 동일한 문자열이 Lua의 `ARGV[1]`로 전달된다.

```lua
local seq = redis.call('INCR', KEYS[2])
redis.call('ZADD', KEYS[1], seq, ARGV[1])
```

`INCR`는 호출할 때마다 증가한다. 반면 ZSet은 **member를 기준으로 유일성**을 유지한다.
`ZADD`에 이미 있는 member를 넘기면 새 항목을 추가하지 않고 기존 항목의 score를 갱신한다.

처음에는 `m:__rand_int__`가 score 1로 생기고, 이후 같은 멤버의 score가 2, 3, …, 1,000으로
변한다. 실제 마지막 멤버는 하나였고 score는 1,000이었다.
이 결과는 요청 999건이 Redis에서 유실된 것이 아니라 같은 사람을 반복 갱신한 것이다.

### 2. `-r 1000`은 서로 다른 1,000개를 순서대로 발급하지 않는다

이 옵션은 매번 0~999 범위에서 난수를 뽑아 치환한다. 이미 뽑은 값도 다시 나올 수 있다.
이번 실행에서는 서로 다른 값이 608개였고, 나머지 392번은 기존 멤버를 갱신했다.

균등하고 독립적으로 추출한다고 가정하면, 후보 K개에서 N번 뽑을 때 서로 다른 값의 기대 개수는
다음과 같다.

```text
K × (1 - (1 - 1/K)^N)

K = 1,000, N = 1,000 → 약 632.3개
```

따라서 요청 수와 난수 범위를 모두 1,000으로 맞춰도 1,000명이 쌓이는 것이 아니다.

### 3. 난수 범위를 키워도 중복을 보장해서 없애지는 못한다

`-r 1000000`에서는 가능한 값이 백만 개로 늘어 중복 가능성이 줄어든다.
하지만 이번 실행에서도 한 번 중복되어 실제 대기자는 999명이었다.
다른 실행에서는 1,000명이 나올 수도 있지만, 한 번 중복이 없었다고 고유성이 보장되는 것은 아니다.

## 프로젝트에 적용할 판단 기준

- `seq = 1000`은 이 실험에서 INCR가 1,000번 실행됐음을 보여 준다. 고유 대기자 수는 아니다.
- 고유 대기자 수는 `ZCARD waiting`으로 따로 확인해야 한다.
- 서로 다른 N명을 넣는 실험이라면 토큰 생성 방식과 실제 데이터 개수를 함께 검증해야 한다.
- 동일 Lua를 사용해도 고유 멤버 추가와 기존 멤버 갱신은 서로 다른 워크로드다.
- 이 차이를 해결하기 전에는 기존 벤치마크로 “대기열 깊이 150만 건”이나
  “동일 조건에서 Redis 단독 성능의 99%”를 재현했다고 말할 수 없다.

이 단계에서는 원인 재현과 데이터 검증을 완료했다. 기존 성능 스크립트와 애플리케이션은
변경하지 않았다. 성능 스크립트 수정과 AWS 재측정은 후속 단계다.

직접 설명해 볼 질문: **“seq가 1,000이고 waiting이 608이면, 요청 392건이 실패한 것인가?”**
이번처럼 모든 호출이 완료되고 승격·회수·만료가 없는 실험에서는 아니다.
392번의 요청은 이미 존재하는 대기 멤버의 score를 갱신했다.

참고: [Redis benchmark의 -r 옵션](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/benchmarks/).
