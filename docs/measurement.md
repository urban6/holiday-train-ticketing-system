# 측정

> [← README](../README.md)

부하 도구는 k6입니다. 시나리오가 둘입니다.

```bash
# 앱을 loadtest 프로파일로 띄운 뒤

# 진입: N명분 요청을 최대한 빠르게 밀어넣는다
k6 run -e USERS=100000 k6/enqueue.js

# 조회: N명이 대기하면서 5초 간격(지터 포함)으로 자기 순번을 폴링한다
k6 run -e WAITERS=5000 k6/status.js
```

두 수치를 같은 축에 놓고 비교하면 안 됩니다.
진입은 1인당 1회지만 조회는 1인당 N회라, 초당 조회 수가
`대기 인원 ÷ 폴링 주기`만큼 곱해집니다.

앱은 **IDE Run 버튼이 아니라 빌드된 jar로** 띄웁니다.
IDE는 `-XX:TieredStopAtLevel=1`을 붙이는데, C2 컴파일러를 꺼서
아무리 워밍업해도 최적화된 코드에 도달하지 못하기 때문입니다.

```bash
cd waiting-server && ./gradlew bootJar && cd ..
java -jar waiting-server/build/libs/waiting-0.0.1.jar \
     --spring.profiles.active=loadtest
```

`loadtest` 프로파일은 측정을 왜곡하는 것만 끕니다.
특히 요청당 `log.debug`를 끄는 게 중요한데, `System.out`의 락이
가상 스레드에서 pinning 지점이라 켜두면 대기열이 아니라 로거를 측정하게 됩니다.

## 워밍업 (2026-07-26 추가)

**앱을 재기동했다면 수십만 건을 먼저 태우고 측정해야 합니다.** 같은 JVM에서 재기동 없이
동일한 런(15만 건, VUS 1,000)을 세 번 연속 돌린 결과입니다.

| 런 | rps | avg |
|---|---|---|
| 1 | 16,215 | 61.21ms |
| 2 | 26,000 | 37.83ms |
| 3 | 29,181 | 33.35ms |

같은 코드·같은 부하인데 **1런과 3런이 1.8배** 차이 납니다. 계속 오르고 있어서
정상 상태에 닿으려면 45만 건 이상이 필요합니다. 수백 건짜리 워밍업은 아무 효과가 없습니다.

측정 직전에 JVM을 재기동했다면 **본 측정과 같은 형태의 부하로 60만 건 정도**를 먼저 태웁니다.
재기동하지 않고 여러 조건을 이어서 잴 때는 뒤 조건일수록 유리해지므로,
조건 순서를 바꿔 가며 번갈아 재야 합니다.

> 아래 **로그인 도입 후 회귀 확인**(2026-07-23) 표는 워밍업 300건으로 측정한 것이라
> 이 구간에 그대로 들어갑니다(14,864~20,712). 그 표의 큰 산포는 머신 상태 노이즈가 아니라
> **JIT 램프였을 가능성이 큽니다.** "측정 가능한 차이가 없다"는 결론 자체는 바뀌지 않지만,
> 산포의 원인 설명은 정정이 필요합니다.

큐에 실제로 쌓였는지, 그리고 다시 돌리기 전 초기화:

```bash
W=$(TZ=Asia/Seoul date +%Y%m%d)
docker exec redis redis-cli ZCARD waiting:holiday:$W   # 대기 인원
docker exec redis redis-cli ZCARD active:holiday:$W    # 활성 인원 (capacity를 넘으면 안 됨)

# 초기화. active 키까지 지워야 하므로 패턴이 'waiting:'이 아니라 '*:holiday:*'다.
docker exec redis redis-cli --scan --pattern '*:holiday:*' \
  | xargs -n1 docker exec redis redis-cli UNLINK
```

키 TTL이 "내일 자정 + 1시간"이라 초기화하지 않으면 같은 날 계속 누적됩니다.

정원을 바꿔 가며 보려면 실행 인자로 덮어씁니다.

```bash
java -jar waiting-server/build/libs/waiting-0.0.1.jar \
     --spring.profiles.active=loadtest \
     --queue.capacity=1000 --queue.max-batch=500 --queue.admission-grace=150s
```

## 아직 재지 않은 것 — 조회 경로에 얹은 쓰기의 비용

대기열 이탈 처리가 붙으면서 `status.lua`에 `ZADD` 한 줄이 들어갔습니다
([대기열 이탈 처리](design.md#대기열-이탈-처리)). 조회 경로가 읽기 전용이 아니게 된 대가인데,
**그 크기를 아직 재지 않았습니다.** 설계 문서가 "조회마다 비용"이라고만 적고 미뤄 뒀던 값입니다.

재는 방법은 이렇습니다. 조회 부하이므로 `k6/status.js`를 씁니다.

```bash
# A: ZADD 있는 현재 코드
# B: status.lua의 ZADD 한 줄만 주석 처리한 jar
k6 run -e WAITERS=5000 -e DURATION=2m k6/status.js
```

- **같은 세션 안에서 A와 B를 번갈아 3회씩.** 절대값은 세션을 넘어 비교할 수 없습니다.
- 재기동했다면 **본 측정과 같은 형태로 60만 건 선행**(위 [워밍업](#워밍업-2026-07-26-추가)).
  1런과 3런이 1.8배 차이 나던 그 구간에 들어가면 A/B 차이가 JIT 램프에 묻힙니다.
- 매 런 전 Redis 초기화. `seen` 키도 `*:holiday:*` 패턴에 함께 걸립니다.
- 진입 처리량(`enqueue.js`) 수치와 같은 축에 놓지 말 것 — `enqueue.lua`에도 `ZADD`가 하나
  늘었지만 진입은 1인당 1회고 조회는 1인당 N회입니다.

기대치는 작습니다. `ZADD`가 `ZRANK`와 같은 `O(log N)`이고 같은 스크립트 안이라 왕복이 늘지
않으므로, 앱 지연에서 Redis가 차지하는 몫이 5% 남짓이라는 [앞 절](#그런데-앱은-6만-올랐습니다)의
결과대로라면 눈에 띄지 않아야 합니다. **눈에 띈다면 그게 더 흥미로운 결과입니다** —
Redis 명령 수가 아니라 다른 무언가가 걸려 있다는 뜻이기 때문입니다.

## 환경

k6·애플리케이션·Redis가 **모두 같은 Mac에서** 돕니다.
부하 생성기와 측정 대상이 CPU를 나눠 쓰므로 **절대 수치는 실제 서버 성능이 아닙니다.**
목적은 절대값이 아니라 **병목이 어디서 어떤 모양으로 나타나는가**와
**변경 전후의 상대 비교**입니다.

Redis는 컨테이너 CPU 1코어, `maxmemory 256mb` + `noeviction`입니다.
대기열 항목 하나가 약 115바이트라 **약 220만 건**에서 쓰기가 거부되기 시작합니다.
버그가 아니라 설계된 동작입니다.

## 결과

2026-07-22. `loadtest` 프로파일 jar, 요청당 로그 제거,
`kern.ipc.somaxconn=1024` + `server.tomcat.accept-count=1000`.
각 런 30만 건, 매 런 전 Redis 초기화.

| 동시 실행(VUS) | 실효 rps | avg | p95 | 실패 |
|---|---|---|---|---|
| 500 | 33,073 | 14.86ms | 27.64ms | 0 |
| 1,000 | **34,129** | 28.73ms | 51.64ms | 0 |
| 2,000 | 30,912 | 61.80ms | 111.68ms | 0 |
| 4,000 | 29,096 | 131.63ms | 250.44ms | 0 |

동시 실행을 2배로 늘릴 때마다 **응답 시간은 정확히 2배가 되고 처리량은 제자리**입니다.
창구 수가 정해진 은행에 손님만 늘리는 것과 같아서, 줄이 길어질 뿐 처리량은 안 늘어납니다
(`처리량 = 동시성 ÷ 응답시간`). 이 시스템의 최적 지점은 VUS 500~1,000 근처입니다.

네 런 모두 `ZCARD`가 정확히 300,000이었습니다.
초당 3만 건씩 밀어넣는 동안 순번 유실도 중복도 없었습니다 —
`INCR`과 `ZADD`를 Lua로 원자적으로 묶은 것이 의도대로 동작했습니다.

## 입장 제어 검증

2026-07-23. `capacity=1000`, `max-batch=500`, `promote-interval=1s`, `admission-grace=60s`.
만 명을 밀어넣고 2,000명이 90초간 폴링했습니다.

- **정원을 넘지 않았습니다.** 0.5초 간격으로 `ZCARD active`를 200회 관측하는 동안
  최대치가 정확히 1,000이었습니다. `waiting + active = 10,000`도 유지됐습니다.
- **폴링 18만 건 전부 성공**했고 `앞 + 뒤 + 1 = 전체`가 한 번도 어긋나지 않았습니다.
  조회 p95는 58.51ms(임계 500ms).
- **`max-batch`가 실제로 관측됩니다.** 첫 1,000명의 입장권이 만료돼 슬롯이 한꺼번에
  회수된 순간, 대기 인원이 `10,000 → 9,500 → 9,000`으로 **두 주기에 나눠** 줄었습니다.
  상한이 없었다면 1,000명이 한 스크립트에서 처리됐을 자리입니다.

배치가 도는 순간의 지연 스파이크는 이 해상도(1초 간격 관측)로는 분리해 내지 못했습니다.
`max-batch` 값을 근거 있게 정하려면 배치 실행 시각과 요청 지연을 같은 축에 놓고 봐야 합니다.

Redis를 내리고 확인한 것 — 스케줄러가 죽지 않고 주기마다 경고 한 줄만 남기며,
Redis를 되살리면 다음 주기에 스스로 재개합니다. 진입 API는 그대로 503입니다.

> 이 런은 Docker 데몬이 꺼져 있어 **호스트의 Redis**(Homebrew, 포트 6380)로 측정했습니다.
> 위의 진입 처리량 표와 절대값을 나란히 두면 안 됩니다 — 병목의 정체인
> Docker 왕복 비용이 빠져 있습니다.

같은 머신에서 변경 전(HEAD) jar와 변경 후 jar를 **번갈아 3회씩** 돌렸습니다.
각 런 15만 건, VUS 1,000, 매 런 전 워밍업 300건 + Redis 초기화.

| | r1 | r2 | r3 | 평균 |
|---|---|---|---|---|
| 변경 전 | 18,378 | 18,036 | 20,712 | 19,042 |
| 변경 후 | 14,864 | 20,665 | 19,340 | 18,290 |

**측정 가능한 차이가 없습니다.** 두 계열의 산포(14.9k~20.7k)가 평균 차이(4%)보다 훨씬 큽니다.

변경 전 jar조차 오늘은 19k 언저리로 나왔습니다. 같은 코드가 그날 34k, 오늘 19k라면
차이는 코드가 아니라 머신 상태입니다. **비교는 같은 세션 안에서만** 유효합니다.

## 병목

애플리케이션을 빼고 `redis-benchmark`로 같은 Lua 스크립트를 직접 때려 비교했습니다
([k6/redis-baseline.sh](../k6/redis-baseline.sh)).

| 측정 대상 | 처리량 |
|---|---|
| Redis 자체 (컨테이너 안) | 107,009 rps |
| 호스트 → Docker → Redis (앱과 같은 경로) | 37,908 rps |
| Spring Boot 앱 전체 | 34,129 rps |

**병목은 Spring Boot가 아니라 Docker 네트워킹입니다.**
앱의 34k는 호스트에서 Redis에 직접 접속했을 때의 한계인 38k에 거의 붙어 있고,
Spring Boot가 추가로 잡아먹은 건 10% 정도입니다.
반면 컨테이너 안팎에서 3배 가까이 깎입니다.

> **2026-07-26 정정.** 이 문단의 추론은 "앱 34k가 경로 한계 38k에 붙어 있다"는 **상관**에
> 근거한 것입니다. 실제로 Docker를 걷어내 경로 천장을 2.9배 열어 보니 앱 처리량은 **6%만**
> 올랐습니다 — 앱은 이 경로에 묶여 있지 않았습니다. [Docker 천장을 걷어내면](#docker-천장을-걷어내면-2026-07-26) 참고.

요청당 Docker 왕복 비용은 약 0.31ms입니다
(호스트 p50 0.399ms − 컨테이너 p50 0.087ms).
Redis가 실제로 일하는 시간은 **8.37μs**이므로,
**일하는 시간의 약 37배를 오가는 데** 쓰고 있는 셈입니다.

macOS에서 Docker가 리눅스 VM 안에서 도는 구조 때문이며 **리눅스 서버에는 없는 비용**입니다.
따라서 이 환경에서는 코드나 Redis 설정을 최적화해도 34k 위로 올라가지 않습니다.
그 위를 보려면 Redis를 리눅스 머신에 올리거나 부하 생성기를 분리해야 합니다.

> **2026-07-26 정정.** 앞 문장의 두 갈래 중 **Redis 쪽을 실제로 해 봤고, 그것만으로는 오르지
> 않았습니다.** 남은 갈래인 **부하 생성기 분리**가 다음 단계입니다.

## Docker 천장을 걷어내면 (2026-07-26)

위 절의 "병목은 Docker 네트워킹"이 **앱에도 해당되는가**를 검증했습니다.
Redis를 Docker 밖(호스트 네이티브)으로 빼고 같은 k6 시나리오를 그대로 돌렸습니다.
애플리케이션 코드는 바꾸지 않았고 실행 인자만 달랐습니다.

두 Redis의 설정을 맞추는 게 전제였습니다. Homebrew 기본 설정을 쓰면 Docker 네트워킹 말고도
영속성과 `maxmemory`가 같이 바뀝니다 — `/opt/homebrew/etc/redis.conf`의 `save`가 **주석 처리**돼
있는데 이건 꺼짐이 아니라 컴파일 기본값(`3600 1 / 300 100 / 60 10000`)이 살아남는다는 뜻입니다
([infra/redis/redis.conf](../infra/redis/redis.conf)의 같은 경고 참고). 그래서 프로젝트 설정 파일로 띄웠습니다.

```bash
redis-server infra/redis/redis.conf --port 6380 --bind 127.0.0.1
```

포트를 6380으로 비킨 이유는 Homebrew 기본값이 6379라 Docker와 겹치기 때문입니다.
`docker-compose.yml`이 Postgres를 5433으로 비켜 놓은 것과 같은 함정입니다 —
호스트의 `127.0.0.1:6379`가 Docker의 `*:6379`보다 구체적이라 앱이 조용히 그쪽으로 갑니다.
매 런 워밍업 뒤 **어느 Redis에 들어갔는지 `seq`로 확인**하고 본 측정에 들어갔습니다.

### 경로 천장은 확실히 열렸습니다

`redis-benchmark`, `clients=100`, 20만 요청, **모두 같은 세션**:

| 구간 | rps | p50 |
|---|---|---|
| 컨테이너 안 (Docker 네트워크 우회) | 107,238 | 0.743ms |
| 호스트 → Docker → Redis | 36,576 | 2.559ms |
| **네이티브 호스트 Redis (신규)** | **105,764** | 0.727ms |

앞 절의 07-22 수치(107,009 / 37,908)와 거의 같아 머신 상태가 비교 가능함을 확인했습니다.
**네이티브는 컨테이너 내부와 동일한 속도**입니다 — Docker 포트 포워딩이 처리량의 66%를 먹고
있었고, 걷어내면 전부 회수됩니다. 앱 경로의 천장이 **36,576 → 105,764로 2.9배** 열렸습니다.

### 그런데 앱은 6%만 올랐습니다

VUS 1,000, 각 런 15만 건, **A(Docker 6379)와 B(네이티브 6380)를 번갈아** 3회씩:

| | r1 | r2 | r3 | 평균 |
|---|---|---|---|---|
| A · Docker | 27,156 | 27,308 | 26,748 | 27,071 |
| B · 네이티브 | 30,177 | 28,884 | 27,345 | **28,802** |

차이는 **+6.4%**입니다. 전 런 실패 0, `seq`는 매번 정확히 150,000이었습니다.
산포가 겹치지 않는다는 점은 유의미합니다 — `min(B) 27,345 > max(A) 27,308`으로 두 계열이
완전히 분리됩니다. 방향은 일관되지만 **크기가 작습니다.**

수치가 서로 맞물립니다. `redis-benchmark`의 p50 차이가 요청당 **1.83ms**(2.559 − 0.727)이고,
앱은 요청당 Redis 호출이 1회입니다. 실제로 관측된 앱 평균 지연 감소가 **1.92ms**
(A 35.82ms → B 33.89ms)로 거의 같습니다. 35ms 요청에서 1.9ms면 5%이고, 처리량 +6%와 일치합니다.

**즉 Redis 경로는 앱 지연의 5% 남짓입니다.** 경로 천장을 2.9배 열어도 앱이 6%만 오른 이유가
이것이고, 앞 절이 "앱 34k ≈ 경로 38k"를 근거로 내린 인과 추론은 성립하지 않습니다.

### knee는 움직이지 않았습니다

네이티브 Redis에서 VUS를 쓸었습니다(워밍 상태, 각 15만 건):

| VUS | rps | avg | p95 |
|---|---|---|---|
| 500 | 33,800 | 14.44ms | 27.49ms |
| **1,000** | **36,087** | 26.75ms | 47.72ms |
| 2,000 | 33,534 | 58.13ms | 103.14ms |
| 4,000 | 25,073 | 150.17ms | 279.54ms |

천장을 열었는데도 knee는 여전히 **VUS 1,000 근처**입니다. 스윕은 재기동 없이 순서대로 돌아
뒤 단계일수록 JVM이 더 데워졌는데도 느려졌으므로, 이 판정은 워밍업 기울기에 대해 견고합니다.

### 교란 변수

- **버전**: 호스트 8.6.2(Homebrew) vs 컨테이너 8.8.0-alpine. 통제하지 못했습니다.
- **CPU 상한**: 컨테이너는 `cpus: "1.0"`, 호스트 Redis에는 상한이 없습니다.
- **`kern.ipc.somaxconn`이 128**입니다(위 진입 처리량 표는 1024). 다만 전 런에서 실패가 0이라
  이 동시성에서는 백로그가 제약이 아니었습니다.
- **k6·앱·Redis가 모두 같은 Mac**입니다. Docker 왕복이 사라지면 k6 몫의 CPU도 늘어나므로,
  +6%에 네트워킹 제거 외의 몫이 섞여 있을 수 있습니다.

### 남은 것

앱 지연 35ms 중 Redis는 1~3ms입니다. 나머지 90% 이상이 Tomcat·가상 스레드·루프백 TCP,
그리고 **같은 머신에서 도는 k6와의 CPU 경합**에 있습니다. 같은 Mac에 있는 한 이 둘을 더
쪼갤 수 없습니다 — 다음 단계는 [README의 인프라 그림](../README.md#인프라-아키텍처)대로
**부하 생성기를 분리**하는 것입니다.
